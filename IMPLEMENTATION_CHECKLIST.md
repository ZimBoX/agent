      максимум 30с, как в разделе 8.1 плана) — `WithAutomaticReconnect(...)`
- [x] Событие "токен отозван" → клиент разлогинивается мгновенно — `AdminController`

- [x] **Найден и исправлен критический баг**: установленный (через `Setup.exe`) v1
      падал при запуске с нативным исключением `0xC000027B` в `Microsoft.ui.xaml.dll`
      (подтверждено через `Get-WinEvent -LogName Application`, Event ID 1000). Debug-сборка
      работала, Release publish — нет → сравнение содержимого папок публикации показало,
      что `ClaudeAssistant.Client.pri` (собственный `.pri`-индекс XAML-ресурсов
      приложения, отдельный от `.pri` фреймворка WinUI3, который на месте) отсутствовал
      в `win-x64\publish\`. Причина: при вызове только `-t:Publish` (без `-t:Build,Publish`)
      MSBuild считает `.pri` уже актуальным в родительской (не-RID) папке сборки и
      пропускает шаг копирования в `win-x64\publish\` из-за инкрементальной проверки
      "up to date". Требует внимания при каждой будущей сборке релиза — надёжно
      собирать только комбинированным таргетом `-t:Build,Publish`, при сомнении сверять
      наличие `ClaudeAssistant.Client.pri` в папке публикации до `vpk pack`
- [x] **Найден и исправлен баг лимита загрузки**: `POST /api/admin/releases/upload`
      падал с 400 "Multipart body length limit 134217728 exceeded" на архиве размером
      ~100+ МБ — у ASP.NET Core `RequestSizeLimit` и `FormOptions.MultipartBodyLengthLimit`
      это два независимых лимита (второй по умолчанию 128 МБ). Исправлено добавлением
      `[RequestFormLimits(MultipartBodyLengthLimit = 1024*1024*1024)]` рядом с
      `[RequestSizeLimit]`
- [x] **Найден и исправлен баг, из-за которого автообновление молча не работало**:
      после SignalR-события `UpdateAvailable` установленный клиент не обновлялся —
      ни ошибки, ни перезапуска. Диагностировано через лог Velopack
      (`%LocalAppData%\velopack\velopack_ClaudeAssistant.Client.log`): скачка и delta-,
      и full-пакета падала с `404 Not Found`. Причина — `app.UseStaticFiles` по
      умолчанию не отдаёт файлы с нераспознанным расширением
      (`ServeUnknownFileTypes = false`), а `.nupkg` не входит в стандартный
      `FileExtensionContentTypeProvider`. Исправлено явным маппингом
      `.nupkg`/`.exe` → `application/octet-stream` через кастомный
      `FileExtensionContentTypeProvider`, переданный в `StaticFileOptions.ContentTypeProvider`
- [x] **Проверено сквозным тестом на реально установленном приложении**: установлен
      v1.0.0 через `Setup.exe --silent`, собран и загружен v2.0.0 (Velopack сгенерировал
      дельта-пакет: "1 patched, 730 unchanged"), `POST /api/admin/releases/upload` →
      рассылка `UpdateAvailable` → работающий v1-клиент (без участия пользователя,
      без перезапуска вручную) скачал и применил обновление и перезапустился сам —
      подтверждено новым PID процесса, новым `StartTime`, `UpdateManager.CurrentVersion`
      = "2.0.0" и обновлённым `last-known-version.txt`
- [x] **Откат (rollback) на случай бажного релиза** — клиент: `UpdateOptions.AllowVersionDowngrade
      = true` (штатный флаг Velopack именно под этот сценарий); backend:
      `GET /api/admin/releases` (версии, видимые в фиде) и
      `POST /api/admin/releases/{version}/retract` (убирает версию из
      `releases.win.json`, сами файлы пакетов не удаляет — можно откатить обратно ещё
