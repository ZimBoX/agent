# Проект: Windows-оболочка для Claude API (внутренний инструмент компании)

Статус: планирование. Кода ещё нет, документ фиксирует архитектурные решения по мере обсуждения.

## 1. Концепция

Нативное Windows-приложение, встраивающееся в рабочий процесс через Explorer, которое
упрощает сотрудникам разных должностей работу с Claude API через готовые шаблонные
промпты (например: юрист → быстрая вычитка договора на спорные моменты).

Аудитория: одна компания, внутренний инструмент (не SaaS).

## 2. Архитектура компонентов

- **Shell Extension** (C++/C# COM, `IExplorerCommand`) — пункт в контекстном меню
  Explorer, передаёт путь(и) к выбранным файлам **или папке** в клиентское приложение
  (поддержка multi-select и выбора папки).
- **Клиентское приложение** (WinUI 3 / WPF, .NET) — минималистичное окно: список
  файлов → выбор шаблона → прогресс обработки → результат, история.
- **Backend API** — авторизация, хранилище шаблонов, обработка файлов, проксирование
  запросов к Claude API, логи/лимиты.
- **База данных** (PostgreSQL) — пользователи, устройства/токены, шаблоны, история
  запросов.
- **Веб-панель админа** — управление сотрудниками, выдача кодов привязки устройств,
  отзыв токенов, (позже) редактирование шаблонов.

## 3. Интеграция с Explorer — решение

Комбинация:
- Пункт контекстного меню через `IExplorerCommand`, доступный при:
  - выборе одного файла,
  - выборе нескольких файлов (multi-select),
  - выборе папки.
- Отдельное компактное окно приложения (не хак с враппером в само окно Explorer —
  неофициальный путь, хрупкий при обновлениях Windows).

**Обработка папки**: при выборе папки приложение сканирует **только верхний уровень**
(без рекурсии в подпапки) и показывает пользователю список найденных файлов с
чекбоксами — пользователь сам отмечает, какие именно файлы войдут в запрос, перед
отправкой.

**Реализовано и проверено на реальном Проводнике (Этап 8)** — `IExplorerCommand` на
C#/.NET через `EnableComHosting` (comhost.dll), регистрация в `HKCU\Software\Classes`
(без прав администратора). Подтверждено вживую: пункт меню появляется (на Windows 11 —
в подменю "Показать больше опций", как и любой классический не-Microsoft пункт),
клик по нему запускает клиент с переданными файлами, **multi-select работает одним
вызовом** — все выбранные файлы приходят в одном `IShellItemArray`, а не запускают
клиент много раз. Это и было основной причиной выбрать более сложный/рискованный
COM-путь вместо простой регистрации через реестр + IPC между процессами.

Технический риск (`explorer.exe` грузит .NET-рантайм в свой процесс) подтвердился
только как повышенная сложность отладки — при тестировании через `pwsh` (сам
.NET-процесс) активация COM падала с `CoreHostIncompatibleConfig` (конфликт версий
рантайма при попытке загрузить CLR в процесс, где CLR уже загружен). Это оказалось
артефактом методики тестирования, а не багом: `explorer.exe` — нативный процесс без
CLR, конфликта там нет. Диагностировано вызовом `DllGetClassObject` напрямую из
классического Windows PowerShell 5.1 (не .NET-процесс) в обход всей активационной
цепочки COM — так и было доказано, что сама сборка/регистрация корректны, прежде чем
рисковать реальным `explorer.exe`.

Известный технический долг: если клиент уже запущен (висит в трее) и пользователь
снова кликает пункт меню, `Invoke` сейчас безусловно стартует **второй** процесс
клиента (дублирующий трей-значок) вместо пересылки файлов в уже работающий —
приемлемо для MVP, но стоит закрыть до реального релиза (см. чеклист).

## 4. Auth — решение

- **1 токен = 1 ПК.** Новая установка на другом устройстве инвалидирует токен предыдущей
  установки той же учётки (re-bind, старый токен помечается `revoked`).
- **Флоу привязки**: админ в веб-панели создаёт учётку сотрудника → генерирует
  одноразовый короткоживущий код привязки → сотрудник вводит код при первом запуске
  приложения → клиент генерирует токен → отправляет на backend вместе с кодом → backend
  привязывает токен к учётке, код сгорает.
- **Хранение на клиенте**: токен зашифрован через Windows DPAPI, привязан к
  Windows-логину пользователя на конкретной машине.
- **Backend**: таблица `devices/tokens` — `user_id`, `token_hash` (хранится хэш, не
  сырое значение), `created_at`, `revoked_at`, `last_seen_at`.
- **Отзыв доступа**: ручной отзыв токена из веб-панели админа (увольнение/утеря
  устройства).

## 5. Шаблоны (предпромпты) — решение

- Хранятся **на сервере** (не в клиенте) — по сути, преднастроенные системные промпты.
- Привязаны к должности/отделу — **многие-ко-многим** (один шаблон может относиться
  сразу к нескольким отделам, реализовано как `Template.Roles` через join-таблицу).
  Пользователь в клиенте видит только шаблоны своей должности.
- Должности (`Role`) — управляемый список через админку (`/admin/roles`), не
  свободный текст, чтобы не плодить опечатки. У должности есть флаг `IsAdmin` —
  такая должность видит вообще все шаблоны, независимо от привязки (нужно для
  администраторов/руководства, которым важен полный обзор).
- Структура: `id`, `title`, `roles` (many-to-many), `system_prompt` (с
  плейсхолдером `{{document_text}}`), `model`, `created_at`, `version` (растёт
  при каждом редактировании).
- Редактирование шаблонов админом — **реализовано** (`/admin/templates`),
  включая защиту от удаления уже использованного шаблона.
- **Пересмотрено**: изначально предполагалась полная библиотека шаблонов под
  каждую должность, но заранее угадать всё, что понадобится каждому отделу,
  оказалось нереалистично. Решение — гибрид: держать курируемые шаблоны для
  типовых задач, и добавить в клиенте возможность написать свой произвольный
  промпт для остального (ещё не реализовано, см. чеклист Этап 10). История
  запросов на сервере уже пригодна для того, чтобы понять, какие произвольные
  промпты повторяются чаще всего, и оформить их в шаблоны осознанно, когда
  реальные паттерны использования станут видны.

## 6. Обработка файлов / извлечение контента — решение

- Клиент **не** извлекает текст локально — файл(ы) временно загружаются на API-сервер.
- Backend извлекает текст из каждого файла отдельно, объединяет их (с пометкой
  имени файла как разделителем) в единый контекст, подставляет в шаблон вместе с
  системным промптом, отправляет в Claude API, возвращает результат клиенту.
- Поддержка нескольких файлов в одном запросе — обязательный сценарий (не только
  один файл), т.к. некоторым задачам нужен контекст из нескольких документов сразу.
- Файлы на сервере — временные, не персистентное хранилище. **Реализовано**: файлы не
  пишутся на диск отдельно от фреймворка — обрабатываются напрямую из потока
  `IFormFile.OpenReadStream()` в рамках одного синхронного запроса; собственная
  логика удаления/TTL не понадобилась, буферизацию и очистку берёт на себя ASP.NET
  Core. Актуально, пока обработка синхронная и в один запрос — если позже появится
  очередь/асинхронная обработка, это решение придётся пересмотреть.

**Форматы в MVP**: DOCX, PDF, XLSX — реализовано и проверено (Open XML SDK /
ClosedXML / PdfPig). Легаси **.doc** (старый бинарный формат Word) сознательно не
поддержан — Open XML SDK работает только с .docx, а полноценная поддержка .doc
потребовала бы отдельной библиотеки. Для MVP это приемлемое ограничение.

Для PDF — только текстовый слой (без OCR сканов); если текст не извлекается или файл
повреждён/зашифрован — ошибка "нечитаемый PDF".

**Превышение контекстного окна**: в MVP — просто ошибка "файл слишком большой",
без чанкинга/суммаризации. Чанкинг закладываем как возможное развитие после MVP.

Лимиты — реализовано: 20 МБ на файл, 50 МБ суммарно на запрос, до 10 файлов.

## 7. UX — решение

Минималистичное окно, линейный флоу без лишних экранов:

1. ПКМ на файле(ах)/папке в Explorer → "Отправить в [ассистент]" → открывается окно.
2. **Список файлов**: для папки — чекбоксы для выбора нужных файлов (см. раздел 3);
   для уже выбранных файлов — сразу готовый список, можно убрать лишние.
3. **Выбор шаблона**: список, отфильтрованный по должности пользователя + поиск по
   всей библиотеке.
4. Кнопка "Выполнить" → **индикатор прогресса** с этапами (загрузка файлов →
   извлечение текста → запрос к Claude → ожидание ответа).
5. **Результат**: текст ответа, кнопки копировать/сохранить.

В MVP шаблон = только фиксированный промпт + файлы, без дополнительных полей ввода от
пользователя (без доп. параметров вроде выбора языка) — это осознанно отложено до
после-MVP, когда будет понятно, что реально нужно пользователям.

## 8. Стек — ФИНАЛ

Единый стек на C#/.NET across клиент, shell extension и backend — один язык, общие
модели данных (DTO переиспользуются), проще одному разработчику вести весь проект.

- Клиент: .NET 8 + WinUI 3
- Shell extension: C# (COM interop через CsWin32) — в одном решении с клиентом
- Backend: **ASP.NET Core (.NET 8) Web API**
- Postgres-доступ: EF Core (Npgsql provider)
- Push-канал (обновления/логаут): **SignalR**
- Автообновление: **Velopack**
- Извлечение файлов: Open XML SDK (docx), ClosedXML (xlsx), PdfPig (текстовый слой pdf)
- Auth: device-bound токен (см. раздел 4), без паролей

### 8.2 LLM-провайдер — решение (пересмотрено)

Вместо прямого Claude API — **агрегатор AITunnel** (`https://api.aitunnel.ru/v1`),
OpenAI-совместимый протокол. Причина: гибкость (простые шаблоны можно будет отдавать
дешёвым моделям вроде Qwen/GPT, сложные — семейству Claude) и экономия без
необходимости интегрировать нескольких провайдеров напрямую.

- SDK: официальный **`OpenAI` NuGet-пакет** с кастомным `Endpoint` (агрегатор говорит
  по OpenAI-протоколу) — не собственная обёртка над `HttpClient`
- Ключ агрегатора — только через переменную окружения (`AITUNNEL_API_KEY`), никогда в
  appsettings.json/git
- Модель — **поле на самом шаблоне** (`Template.Model`), не глобальная настройка.
  Сейчас везде статично `claude-sonnet-5`; когда дойдём до полноценной библиотеки
  шаблонов (раздел 5 / Этап 10), each шаблон сможет указывать свою модель — код уже
  на это рассчитан, миграций не потребуется
- Проверено сквозным тестом: реальный вызов через агрегатор к `claude-sonnet-5`
  вернул содержательный ответ на тестовом документе

## 8.1 Значения по умолчанию (разблокируют реализацию, легко поменять позже)

- Лимит на файл: 20 МБ; суммарно на запрос: 50 МБ
- Максимум файлов в одном запросе: 10
- Удаление временных файлов: сразу в `finally` после обработки + фоновая уборка раз в
  час на случай сбоя (TTL 1 час)
- Неподдерживаемые форматы в списке файлов папки: показываются в списке, но неактивны
  (disabled), с подсказкой "формат не поддерживается" — не прячем, чтобы не путать
- Уведомление при применении обновления: тихий рестарт + маленький ненавязчивый toast
  "Обновлено до vX.Y"
- Реконнект SignalR: экспоненциальный backoff (1с → 2с → 4с ... максимум 30с)
- История запросов: хранится только на сервере (без локального кэша на клиенте)
- Шаблоны: **отложены** — для старта реализации используем 1-2 захардкоженных шаблона
  в БД, чтобы можно было гонять весь флоу end-to-end; полноценная библиотека и
  админ-редактор — отдельный этап позже

## 9. Автообновление клиента — решение

**Флоу разработчика**: сборка ведётся локально → билд загружается на сервер (release-
хранилище/эндпоинт) → дальше всё автоматически, без ручных действий на стороне
пользователя.

**Доставка обновления — push через постоянное соединение**:
- Пока клиент запущен (а он в основном работает в фоне, как трей-приложение), он держит
  открытым лёгкое постоянное соединение с backend (WebSocket/SignalR) — отдельное от
  обычных HTTP-запросов на обработку файлов.
- Как только на сервер загружен новый билд, backend рассылает всем подключённым клиентам
  событие "доступно обновление" — распространение почти мгновенное, без ожидания опроса.
- Клиенты, которые в этот момент не в сети (ПК выключен, приложение закрыто), при
  следующем запуске делают обычную проверку версии как fallback — не полагаемся
  исключительно на push.

**Скачивание**: получив событие, клиент скачивает новый билд в фоне, не мешая работе —
без всплывающих окон, без прерывания текущего использования.

**Применение обновления**: клиент отслеживает простой флаг `isBusy` (true на время
выполнения запроса к Claude API).
- Если `isBusy = false` в момент, когда обновление готово — применяется сразу
  (тихий рестарт приложения с новой версией).
- Если `isBusy = true` — обновление откладывается, применяется сразу после завершения
  текущего запроса (не привязано к закрытию окна — только к отсутствию активного
  запроса, как и просил пользователь).
- **Принудительных обновлений нет** даже для критичных фиксов — всегда ждём момент
  простоя. Это осознанный компромисс: чуть медленнее закрываем критичные баги ценой
  того, что никогда не рвём работу пользователя посреди запроса.

**Технически** — вместо самодельного решения имеет смысл использовать готовый
инструмент для self-update .NET-приложений вне Microsoft Store:
- **Velopack** (актуальный форк идей Squirrel.Windows) — упаковка дельта-обновлений,
  фоновая скачка, применение и рестарт по команде из кода в удобный момент. Закрывает
  большую часть этой логики "из коробки", остаётся только: (1) сервер отдаёт release-feed,
  (2) push-уведомление о новом фиде через WebSocket, (3) клиент сам решает *когда*
  вызвать применение (используя `isBusy`).

**Побочный бонус постоянного соединения**: тот же канал можно использовать для
мгновенного разлогина при отзыве токена админом (раздел 4) — не нужно ждать следующего
HTTP-запроса, чтобы клиент узнал об отзыве.

**Реализовано и проверено сквозным тестом (Этап 7 чеклиста)** — включая живой цикл
v1.0.0 → v2.0.0 на реально установленном приложении. Одна практическая деталь, о
которой стоит помнить: статика ASP.NET Core (`UseStaticFiles`) по умолчанию не отдаёт
файлы с нераспознанным расширением, а `.nupkg` в стандартный
`FileExtensionContentTypeProvider` не входит — без явного маппинга release-feed
молча отвечает 404 на скачивание пакетов, и обновление никогда не применяется, хотя
SignalR-событие доходит нормально.

**Откат (rollback)** — на случай, если выпущенный релиз оказался бажным: Velopack
поддерживает это "из коробки" через `UpdateOptions.AllowVersionDowngrade`. Backend
хранит все когда-либо загруженные версии (upload не удаляет старые файлы — это и так
нужно было для дельт), поэтому откат — это просто "убрать версию из
`releases.win.json`" (`POST /api/admin/releases/{version}/retract`) и заново
разослать `UpdateAvailable`: уже обновившиеся клиенты увидят прежнюю версию как
"последнюю" и накатят её как обычное обновление, только в обратную сторону.
Проверено сквозным тестом (v3.0.0 → retract → откат до v2.0.0 на реально
установленном приложении). Кнопка отката в веб-панели — Этап 9.

## 10. Инфраструктура — решение

- **Один сервер, on-prem** (компания размещает у себя), рассчитан на до ~20 пользователей.
- Характеристики: 2 vCPU, 4 ГБ RAM, 40–60 ГБ SSD, **Ubuntu Server LTS 24.04**.
- Стек поднимается через **Docker Compose**: контейнер `ClaudeAssistant.Api` (backend +
  SignalR hub) + контейнер `postgres`, отдельные volume под данные БД и под
  release-билды (Velopack feed).
- Разделять API и БД на разные машины на этом масштабе смысла нет — легко мигрировать
  позже, если понадобится.

**Доступ — только локальная сеть на первом этапе.** Публично сервер наружу не
пробрасывается.
- TLS: самоподписанный сертификат (нет внешнего домена/CA для внутреннего сервера) —
  устанавливается в доверенные корневые сертификаты на каждой из ~20 рабочих машин как
  часть установки клиента (`certutil -addstore` в инсталляторе).
- Сервер адресуется по внутреннему статическому IP или внутреннему DNS-имени (не
  захардкоженному в клиенте отдельной строкой — чтобы потом просто поменять адрес).

**На будущее — внешний доступ.** Если понадобится доступ снаружи (удалёнка), у
пользователя уже есть отдельный API-сервер со своим доменом и валидными
сертификатами — тогда backend можно будет разместить/запроксировать через него вместо
самоподписанного сертификата. Сейчас это не делаем, только держим в уме при выборе
адреса сервера в конфиге клиента (не жёстко зашивать IP в билд — выносить в
конфигурируемую настройку, чтобы переезд на другой адрес позже не требовал пересборки
клиента).

**Бэкапы**: on-prem = ответственность компании. `pg_dump` по расписанию (cron), хранить
отдельно от самого сервера (внешний диск/другая машина) — минимальная защита от потери
единственной машины.
